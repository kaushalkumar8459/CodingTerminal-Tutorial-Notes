# Day 111 — HttpClient Services and API Boundaries

## Interview Goal
Design a clean data-access boundary between Angular features and backend APIs.

## Level 1 — Basic Questions
1. Why create an API service instead of calling HttpClient directly from components?
2. What responsibility should a data-access service own?
3. What is an API boundary?
4. Why should components avoid knowing URL construction details?
5. What is the benefit of typed service methods?

## Level 2 — Understanding
1. Compare a component that calls HttpClient directly with one that uses JobApiService.
2. Where should request and response mapping happen?
3. Should an API service expose raw HttpClient objects or feature-oriented methods?
4. How does a service boundary improve testing?
5. When should a feature have more than one data-access service?

## Level 3 — Practical
1. Create a typed JobApiService.
2. Separate list, detail, create, update, and delete methods.
3. Keep endpoint paths centralized.
4. Map API DTOs to UI models.
5. Define a service contract that can be mocked in tests.

## JobHub Scenarios
1. Candidate and recruiter screens use different job operations. How would you structure the API boundary?
2. Backend DTO names differ from UI model names. Where should mapping occur?
3. Three features need the same endpoint. How do you avoid duplicated transport logic?
4. A backend endpoint changes. How can the service boundary reduce UI changes?

## Interviewer Follow-Ups
- What is the difference between a service and a facade?
- Should API services contain business rules?
- How would you mock the API boundary?
- How would you prevent an API service from becoming a giant class?

## Coding Question
Design a typed JobApiService with separate methods for job search, details, create, update, and delete.

## Debugging Scenario
A component contains URL strings, HttpParams construction, DTO mapping, notifications, and navigation. Identify the violated boundaries.

## Common Interview Traps
- Treating services as dumping grounds.
- Returning backend DTOs everywhere.
- Mixing navigation with data access.
- Hiding business rules inside transport code.

## Project Connection — JobHub
The API boundary becomes the foundation for later interceptors, authentication, state management, and testing.

## Quick Revision
Feature code should depend on clear data-access contracts rather than raw HTTP transport details.

## Interview Readiness
You are ready when you can explain where API transport ends and feature behavior begins.
