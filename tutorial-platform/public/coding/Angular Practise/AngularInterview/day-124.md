# Day 124 — Role and Permission-Based Access

## Interview Goal
Understand authorization modeling beyond simple authenticated/not-authenticated checks.

## Level 1 — Basic Questions
1. What is a role?
2. What is a permission?
3. Why are roles and permissions different?
4. What is role-based access control?
5. Why should frontend authorization be treated as a UX concern as well as a security concern?

## Level 2 — Understanding
1. Compare role checks with permission checks.
2. Why can a user have multiple roles or permissions?
3. Why should permission names be centralized?
4. How should the UI behave when a user lacks permission?
5. Why must the backend independently enforce permissions?

## Level 3 — Practical
1. Define typed JobHub roles.
2. Define typed permissions such as jobs.create, jobs.publish, and users.manage.
3. Build a reusable permission-checking abstraction.
4. Protect routes based on permissions.
5. Hide or disable actions based on permission without treating that as security.

## JobHub Scenarios
1. Two recruiters can create jobs, but only senior recruiters can publish them. How would you model that?
2. An admin can manage users but not necessarily billing. Why might permissions be more useful than one large Admin role?
3. A user loses a permission while the application is open. How should the UI respond?
4. A button is hidden, but the API still accepts the action. What backend control is missing?

## Interviewer Follow-Ups
- RBAC versus permission-based authorization?
- Where should permission definitions live?
- Can the frontend safely calculate permissions?
- How would you test permission-driven UI?

## Coding Question
Create a typed permission model and a reusable hasPermission abstraction for JobHub.

## Debugging Scenario
A candidate can see the recruiter route after changing a local role value. Explain why client-side role data is not an authorization boundary.

## Common Interview Traps
- Treating hidden UI as security.
- Hard-coding role checks throughout templates.
- Using strings everywhere without a centralized permission model.
- Assuming one role always maps to one fixed permission set.

## Project Connection — JobHub
Permission modeling prepares JobHub for recruiter workflows and admin access management.

## Quick Revision
Roles group responsibilities; permissions describe allowed actions; backend enforcement remains authoritative.

## Interview Readiness
You are ready when you can design authorization around capabilities instead of scattered role checks.
