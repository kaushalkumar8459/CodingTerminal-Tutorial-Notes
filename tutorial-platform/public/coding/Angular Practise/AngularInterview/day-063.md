# Day 63 Interview Questions — Service-Owned Signal State

## Interview Goal
Understand how Angular services can own signal state and expose controlled reactive APIs.

## Interview Questions

### 1. Why can a service own signal state?
**Expected Answer:** A service can own shared reactive state while keeping mutation and business rules behind a controlled API.

### 2. Why avoid exposing writable signals everywhere?
**Expected Answer:** Unrestricted writes let consumers bypass the service's invariants and make state ownership unclear.

### 3. What is computed useful for?
**Expected Answer:** It derives values such as filtered collections, counts, and other state from source signals.

### 4. How should async state be modeled?
**Expected Answer:** Represent meaningful states such as loading, success, empty, and error rather than unrelated boolean flags.

### 5. Common anti-pattern?
**Expected Answer:** Putting unrelated application state into one giant service.

### 6. JobHub scenario
**Expected Answer:** A feature service can own selected-job state and expose readonly state plus explicit commands.

## Interviewer Follow-Ups
- Who owns the state?
- Why use a service instead of a global store?
- How would you test signal updates?
- When should state move to SignalStore?

## Common Interview Trap
A service-owned signal is not automatically global state. Its provider scope determines where the instance is shared.
