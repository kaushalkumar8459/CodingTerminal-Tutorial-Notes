# Day 118 — API Architecture and Data Access

## Interview Goal
Combine HTTP knowledge into a maintainable Angular data-access architecture.

## Level 1 — Basic Questions
1. What is a data-access layer?
2. Why separate API access from UI components?
3. What is the difference between API service and state service?
4. Why are request and response models important?
5. What is a facade in application architecture?

## Level 2 — Understanding
1. Describe the flow from component to API and back.
2. Where should caching decisions live?
3. Where should DTO mapping occur?
4. How should errors cross the data-access boundary?
5. When does a feature need a facade between components and API services?

## Level 3 — Practical
1. Design a JobHub data-access folder.
2. Separate API contracts, API services, mappers, and feature state.
3. Add a facade for a complex job-search feature.
4. Define clear dependencies between UI and data access.
5. Design tests for each boundary.

## JobHub Scenarios
1. Job search, saved jobs, and job details all share job data. How would you prevent duplicated data logic?
2. Recruiter and candidate APIs expose different capabilities. How should boundaries reflect that?
3. A component directly manipulates API DTOs and local state. What would you refactor?
4. A data-access service starts containing UI notifications and navigation. Where should those responsibilities move?

## Interviewer Follow-Ups
- Service versus facade?
- API model versus domain model?
- Where should caching live?
- How do you keep a data-access layer from becoming over-engineered?

## Coding Question
Sketch a JobHub data-access architecture with API services, models, mappers, and an optional facade.

## Debugging Scenario
A small API change requires edits across components, templates, and state stores. Identify missing boundaries.

## Common Interview Traps
- One giant API service.
- One model for transport, domain, and UI.
- Putting UI side effects in data-access code.
- Adding abstraction without a real boundary.

## Project Connection — JobHub
This architecture is reused in the later state-management and enterprise-architecture modules.

## Quick Revision
Good data access creates explicit boundaries between transport, domain data, state, and presentation.

## Interview Readiness
You are ready when you can draw the data flow and explain the ownership of each layer.
