# Day 115 — HTTP Error Handling and Retry

## Interview Goal
Handle transport failures and retries without creating duplicate actions or poor user experiences.

## Level 1 — Basic Questions
1. What is an HTTP error?
2. What is the difference between client-side and server-side failure?
3. What does retry mean?
4. Why should every failed request not be retried automatically?
5. What is the purpose of a user-facing retry action?

## Level 2 — Understanding
1. Which failures may be appropriate for automatic retry?
2. Why can retrying POST requests be dangerous?
3. How should timeout-like failures be represented to users?
4. What is exponential backoff conceptually?
5. Where should common transport error handling live?

## Level 3 — Practical
1. Add explicit error handling to an API service.
2. Retry a suitable transient GET request with a bounded policy.
3. Avoid retrying non-idempotent mutations blindly.
4. Map HTTP errors into UI-friendly error states.
5. Add a manual retry action.

## JobHub Scenarios
1. Job search temporarily fails due to a network interruption. Would you retry automatically?
2. Application submission returns an unknown server error. Should the frontend automatically resubmit?
3. A user clicks Retry five times. How should the UI protect the user and backend?
4. Backend returns 429. What should the application consider?

## Interviewer Follow-Ups
- What is exponential backoff?
- How do idempotency and retry relate?
- Should error messages expose raw backend responses?
- How would you test retry behavior?

## Coding Question
Implement bounded retry handling for a read-only jobs request and expose a final error state.

## Debugging Scenario
A POST request creates duplicate applications after automatic retry. Explain the failure and safer design.

## Common Interview Traps
- Retrying every request.
- Infinite retry loops.
- Treating every 4xx as transient.
- Showing raw backend exception text to users.

## Project Connection — JobHub
Reliable job search and application workflows require deliberate error and retry policies.

## Quick Revision
Retry is a resilience strategy, not a default response to every error.

## Interview Readiness
You are ready when you can choose retry behavior based on request semantics and failure type.
