# Day 68 Interview Questions — Mini Project: Job Management Service Layer

## Interview Goal
Apply service and DI principles to a realistic JobHub job-management feature.

## Interview Questions

### 1. What should a JobManagementService own?
**Expected Answer:** Only the responsibilities assigned to the job-management feature, such as coordinating job operations and feature state.

### 2. Should components call HttpClient directly?
**Expected Answer:** Prefer typed service methods so components depend on meaningful application operations rather than transport details.

### 3. How should job models be typed?
**Expected Answer:** Use explicit interfaces or type aliases for backend, domain, and UI contracts rather than any.

### 4. How should request state be represented?
**Expected Answer:** Use meaningful loading, success, empty, and error states appropriate to the feature.

### 5. Where does authoritative business validation belong?
**Expected Answer:** The backend remains authoritative; client validation improves UX but cannot replace server validation.

### 6. How should the service be tested?
**Expected Answer:** Test successful operations, errors, state transitions, and interactions with controlled dependencies.

### 7. What signals that the service is too large?
**Expected Answer:** It begins owning unrelated candidate, recruiter, admin, navigation, and UI responsibilities.

### 8. JobHub scenario
**Expected Answer:** If save-job, apply-job, and recruiter publish-job become unrelated workflows, review the service boundaries and split responsibilities where appropriate.

## Interviewer Follow-Ups
- Where should API mapping occur?
- How would you introduce SignalStore later?
- How would you mock the API layer?
- Which state belongs locally and which is shared?

## Common Interview Trap
Do not turn a feature service into a dumping ground for every operation related to jobs.

## Self-Assessment
- [ ] I can design a focused service.
- [ ] I can type its public API.
- [ ] I can model request state.
- [ ] I can explain its testing strategy.

## Interview Readiness
**Ready** when you can design the service boundary and defend it in a code review.
