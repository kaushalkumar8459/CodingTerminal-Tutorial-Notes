# Day 128 — Authenticated App Shell and UX

## Interview Goal
Design an application shell that changes safely according to authentication and authorization state.

## Level 1 — Basic Questions
1. What is an authenticated app shell?
2. What UI usually belongs in an authenticated shell?
3. Why should public and protected layouts be separated?
4. What should a user see while authentication state is loading?
5. Why should navigation reflect permissions?

## Level 2 — Understanding
1. Compare public landing pages, login pages, and authenticated application shells.
2. How should navigation items be generated from capabilities?
3. Why should shell rendering wait for required session state?
4. How should the shell react to logout?
5. What should happen to feature routes after session expiry?

## Level 3 — Practical
1. Create public and authenticated route layouts.
2. Build a user/profile menu from authenticated state.
3. Show navigation based on permissions.
4. Add a session-expiry transition.
5. Keep shell UI separate from feature business logic.

## JobHub Scenarios
1. Candidates see Candidate navigation while recruiters see Recruiter navigation. How should the shell determine visibility?
2. Admin navigation loads before permissions are known. What should the UI show?
3. User logs out from the profile menu. Which shell elements should disappear immediately?
4. A user has access to a route but not to one action on that page. How should navigation and action-level permissions differ?

## Interviewer Follow-Ups
- Shell versus feature layout?
- How should navigation state be tested?
- Should hidden menu items be considered authorization?
- How would you prevent shell logic from becoming a monolith?

## Coding Question
Design an authenticated JobHub shell with permission-aware navigation and explicit loading, authenticated, and anonymous states.

## Debugging Scenario
The shell displays recruiter navigation for a candidate until a second render. Identify the race between session bootstrap and navigation computation.

## Common Interview Traps
- Rendering protected navigation before identity is known.
- Putting all feature logic in the shell.
- Treating menu visibility as security.
- Duplicating permission logic in every menu item.

## Project Connection — JobHub
The authenticated shell becomes the stable container for candidate, recruiter, and admin features.

## Quick Revision
The app shell should reflect session and capability state while remaining independent of feature-specific business logic.

## Interview Readiness
You are ready when you can design shell behavior for anonymous, loading, authenticated, expired, and unauthorized states.
