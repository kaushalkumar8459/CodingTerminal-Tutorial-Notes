# Day 116 — httpResource()

## Interview Goal
Understand Angular's signal-oriented HTTP resource API and when it may simplify reactive data fetching.

## Version Note
`httpResource()` is version-sensitive. Verify the Angular version and API status before using it in production code.

## Level 1 — Basic Questions
1. What problem does `httpResource()` address?
2. How is a resource-oriented API different from manually subscribing to HttpClient?
3. How does it relate to Angular Signals?
4. What kinds of state can a resource expose?
5. Why should experimental APIs be isolated carefully?

## Level 2 — Understanding
1. Compare `httpResource()` with a traditional HttpClient service.
2. How can reactive request parameters trigger data refresh?
3. How should loading and error states be represented?
4. What are the trade-offs of adopting a version-sensitive API?
5. When would a normal HttpClient service still be preferable?

## Level 3 — Practical
1. Build a small read-only job-search example using the resource API where supported.
2. Connect reactive search parameters to the request.
3. Render loading, value, and error states.
4. Keep mutation operations in an appropriate API service.
5. Document the Angular version requirement.

## JobHub Scenarios
1. Candidate search should update when filters change. Would a resource abstraction help?
2. The team supports multiple Angular versions. What adoption risk exists?
3. A resource API changes between Angular releases. How would you isolate migration work?
4. A complex workflow has multiple dependent mutations. Would resource APIs be the only abstraction?

## Interviewer Follow-Ups
- Is `httpResource()` the same as HttpClient?
- When should an experimental API be avoided?
- How would you test resource-driven UI state?
- How would you migrate away if the API changed?

## Coding Question
Create a version-aware example showing a reactive read-only job search with explicit loading and error states.

## Debugging Scenario
A project upgrades Angular and the resource API example no longer matches the installed API. Explain how version-sensitive documentation should be handled.

## Common Interview Traps
- Presenting experimental APIs as universally stable.
- Replacing every HttpClient call with resources.
- Ignoring supported-version constraints.
- Mixing experimental and production architecture without boundaries.

## Project Connection — JobHub
This topic introduces modern signal-oriented data fetching while preserving a conventional HttpClient foundation.

## Quick Revision
Use version-sensitive Angular APIs deliberately and keep production architecture easy to migrate.

## Interview Readiness
You are ready when you can explain both the benefit and adoption risk of `httpResource()`.
