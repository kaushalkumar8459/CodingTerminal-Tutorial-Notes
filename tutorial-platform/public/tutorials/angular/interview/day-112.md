# Day 112 — API Models to UI Models

## Interview Goal
Learn why backend DTOs and frontend UI models should sometimes remain separate.

## Level 1 — Basic Questions
1. What is a DTO?
2. What is a UI model?
3. Why might the two models differ?
4. What is data mapping?
5. Where should mapping logic live?

## Level 2 — Understanding
1. What problems occur when backend DTOs are used directly in templates?
2. Why might an API use snake_case while a UI uses camelCase?
3. How should nullable API fields be represented?
4. Why should read-only API fields not automatically become editable form fields?
5. What is the cost of adding a mapping layer?

## Level 3 — Practical
1. Create JobApiResponse and Job UI models.
2. Map API dates into a UI-friendly representation.
3. Map backend status codes into UI states.
4. Map nested API objects into view models.
5. Map form values into create/update API payloads.

## JobHub Scenarios
1. API returns `company_name`, while UI expects `companyName`. Where should conversion happen?
2. API returns internal status codes that should not appear in the UI. How would you model them?
3. Backend adds fields that the UI does not need. Should the UI model change?
4. The same API job is displayed differently in candidate and recruiter screens. Would you use one UI model?

## Interviewer Follow-Ups
- When is a mapping layer unnecessary?
- How do mapping functions affect performance?
- How would you test mappings?
- Should mapping happen in the API service or a separate mapper?

## Coding Question
Create typed mapping functions for API Job DTO → CandidateJob and CandidateJobForm → CreateJobRequest.

## Debugging Scenario
A backend rename forces changes across 20 templates. Explain how a mapping boundary could have limited the impact.

## Common Interview Traps
- Assuming API models are always ideal UI models.
- Hiding mapping logic inside templates.
- Converting data repeatedly in multiple components.
- Ignoring nullability.

## Project Connection — JobHub
Model separation protects the UI from backend contract changes and supports different candidate/recruiter views.

## Quick Revision
API models describe transport contracts; UI models describe what the frontend needs.

## Interview Readiness
You are ready when you can justify model separation based on actual boundary differences rather than creating abstraction for its own sake.
