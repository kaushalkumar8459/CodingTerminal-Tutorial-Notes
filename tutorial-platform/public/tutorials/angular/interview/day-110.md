# Day 110 — Loading, Success, Empty and Error States

## Interview Goal
Design API-backed Angular screens around explicit asynchronous UI states.

## Level 1 — Basic Questions
1. Why is loading state necessary?
2. What is the difference between empty and error state?
3. Why should an API-backed screen not assume data is immediately available?
4. What should happen while a mutation request is running?
5. Why should users have a recovery action after recoverable failures?

## Level 2 — Understanding
1. Model loading, success, empty, and error as explicit states.
2. Why is a single boolean such as `isLoading` often insufficient for complex screens?
3. How should initial loading differ from background refresh?
4. How should retry behavior work?
5. Why should stale data sometimes remain visible during refresh?

## Level 3 — Practical
1. Build a job-list state model with loading, data, empty, and error states.
2. Add a retry action.
3. Add a skeleton for initial loading.
4. Show a non-blocking refresh state when cached data exists.
5. Prevent duplicate mutation submissions.

## Level 4 — JobHub Scenarios
1. Job search initially loads 20 jobs, then refresh fails. Should existing jobs disappear?
2. The API returns HTTP 200 with zero jobs. How should UI distinguish this from failure?
3. A job-details request fails after navigation. What should the page show?
4. A recruiter saves a job successfully but the notification fails. Which operation is successful?

## Level 5 — Interviewer Follow-Ups
- Would you model status as a union type?
- When should stale data be retained?
- How would signals represent asynchronous UI state?
- How would you test each state independently?

## Coding Question
Create a typed `JobListState` using a discriminated union such as `loading | success | empty | error` and render each state with Angular control flow.

## Debugging Scenario
A screen shows a blank page during API failure because the template only handles success. Explain the missing state transition.

## Common Interview Traps
- Treating empty as error.
- Hiding recoverable errors.
- Replacing useful stale data with a blank loading screen.
- Using unrelated booleans that allow impossible states.

## Project Connection — JobHub
This state model becomes the foundation for later HTTP error handling, signals, RxJS, and state-management modules.

## Quick Revision
Explicit asynchronous states make API-backed UIs predictable, testable, and resilient.

## Interview Readiness
You are ready when you can model API state without creating contradictory combinations of flags.
