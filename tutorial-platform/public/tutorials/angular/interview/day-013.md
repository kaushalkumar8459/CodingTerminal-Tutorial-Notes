# Day 13 Interview Questions — Two-Way Binding

## Interview Goal
Be able to explain **Two-Way Binding**, write the relevant Angular code, discuss trade-offs, and apply it to a realistic JobHub feature.

## Interview Questions

### 1. What is two-way binding?
**Expected Answer:** It keeps UI input and application state synchronized in both directions.

### 2. What is the common forms syntax?
**Expected Answer:** The banana-in-a-box syntax [(ngModel)] is commonly used for form controls.

### 3. What enables ngModel?
**Expected Answer:** The Forms package provides the NgModel directive, which must be imported where it is used.

### 4. How is two-way binding conceptually built?
**Expected Answer:** It combines property binding with event binding.

### 5. What is model() in modern Angular?
**Expected Answer:** It defines a writable component model that supports two-way component binding.

### 6. When should two-way binding be avoided?
**Expected Answer:** Avoid it when ownership becomes unclear or when explicit one-way data flow makes the component contract easier to understand.

### 7. How would you build a reusable quantity control?
**Expected Answer:** Expose a writable model value, validate its bounds, and update it only through explicit user actions.

### 8. ngModel vs model()?
**Expected Answer:** ngModel is a forms directive for controls; model() is a component API for a writable input/output-style contract.

### 9. JobHub scenario: a filter component must let the parent both read and update location. Which API fits?
**Expected Answer:** A model() signal is a natural fit when genuine two-way component binding is required.

## Interviewer Follow-Ups
- Why did you choose this approach?
- What alternative Angular approach could solve the same problem?
- What happens when the data changes?
- How would you test this behavior?
- What would you change for a large enterprise application?

## Common Interview Trap
Do not memorize syntax alone. Explain **why** the pattern fits the UI state and which layer owns the underlying data.
