# Day 108 — POST, PUT, PATCH and DELETE

## Interview Goal
Understand how Angular sends mutation requests and how HTTP semantics influence application design.

## Level 1 — Basic Questions
1. What is POST used for?
2. What is the typical purpose of PUT?
3. What is PATCH used for?
4. What is DELETE used for?
5. How do you send a request body with HttpClient?

## Level 2 — Understanding
1. Compare PUT and PATCH.
2. What does idempotent mean?
3. Why should create and update payloads often use different types?
4. Why should the UI not assume every successful mutation returns a full entity?
5. How should the frontend react to common mutation status codes?

## Level 3 — Practical
1. Implement create-job with POST.
2. Implement full job replacement with PUT.
3. Implement partial job updates with PATCH.
4. Implement job deletion with DELETE.
5. Define separate create, update, and response models.

## Level 4 — JobHub Scenarios
1. Recruiters edit only salary and location. Would PATCH or PUT be appropriate based on the API contract?
2. Delete returns no body. How should the UI update local state?
3. Create returns a generated job ID. How should the UI use it?
4. PATCH succeeds but the local job list still shows old data. What synchronization strategies exist?

## Level 5 — Interviewer Follow-Ups
- Is PUT always idempotent?
- Can POST be idempotent in practice?
- How would you handle optimistic versus server-confirmed UI updates?
- Where should mutation errors become user-facing messages?

## Coding Question
Create a typed `JobApiService` with create, update, partial-update, and delete methods.

## Debugging Scenario
A PATCH method sends the complete UI object including read-only fields and the backend rejects it. Identify the contract problem.

## Common Interview Traps
- Treating PUT and PATCH as interchangeable.
- Reusing one type for every API operation.
- Assuming success always returns an entity.
- Updating UI optimistically without a recovery strategy.

## Project Connection — JobHub
Recruiter job management depends on reliable create, update, and delete API flows.

## Quick Revision
HTTP method semantics should match the backend contract; request and response types should reflect each operation.

## Interview Readiness
You are ready when you can choose and implement mutation methods based on API semantics rather than habit.
