# Day 19 Interview Questions — @empty, track and Efficient Lists

## Interview Goal
Be able to explain **@empty, track and Efficient Lists**, write the relevant Angular code, discuss trade-offs, and apply it to a realistic JobHub feature.

## Interview Questions

### 1. What is @empty?
**Expected Answer:** It renders fallback UI when an @for collection contains no items.

### 2. Why is an empty state different from loading?
**Expected Answer:** Empty means the request completed with no items; loading means data is still being obtained.

### 3. Why should loading be explicit?
**Expected Answer:** Otherwise an initial empty array can incorrectly display an empty-result message while the request is still running.

### 4. Why does track matter during refresh?
**Expected Answer:** It lets Angular match incoming items to existing DOM nodes by stable identity.

### 5. Why is tracking by index risky for dynamic lists?
**Expected Answer:** Insertion, deletion, and reordering can change indexes even when the underlying item is the same.

### 6. What makes list rendering expensive?
**Expected Answer:** Large DOM trees, repeated calculations, unnecessary child updates, and unstable identities.

### 7. How should a job list model loading, empty, error, and success?
**Expected Answer:** Use explicit state; render the successful collection with @for and provide @empty for the completed empty result.

### 8. When should virtualization be considered?
**Expected Answer:** When measurement shows that rendering a very large number of DOM items is a bottleneck.

### 9. JobHub scenario: recruiter data refreshes frequently. What should you inspect?
**Expected Answer:** Stable tracking, state churn, request lifecycle, child updates, and measured rendering cost.

## Interviewer Follow-Ups
- Why did you choose this approach?
- What alternative Angular approach could solve the same problem?
- What happens when the data changes?
- How would you test this behavior?
- What would you change for a large enterprise application?

## Common Interview Trap
Do not memorize syntax alone. Explain **why** the pattern fits the UI state and which layer owns the underlying data.
